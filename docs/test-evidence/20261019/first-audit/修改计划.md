## 二、步骤 1：统一 WebSocket 发送前的权限校验

### 修改文件

| 文件 | 修改位置 |
|---|---|
| [ConsultWebSocketHandler.java](../../../../backend/src/main/java/com/petclinic/websocket/ConsultWebSocketHandler.java) | `broadcast`、`write`、`join` 及其调用方 |

新增 `backend/src/main/java/com/petclinic/websocket/ConsultDeliveryGuard.java`，负责发送时的账号、会话准入校验。

### 1.1 收敛发送出口，修复 F1

当前两处出口分别直接调用 `sendMessage`，见 `ConsultWebSocketHandler.write` 和 `ConsultPush.write`。

执行动作：

1. 保留 `ConsultPush` 作为共用发送入口。让 `ConsultWebSocketHandler` 的发送调用委托给它，发送前统一执行权限检查。
2. 新增的 `ConsultDeliveryGuard` 注入 `AccountGuard` 与 `ConsultSessionMapper`。校验参数显式传入接收方 `LoginUser` 和会话 ID。
3. 校验方法使用独立只读事务获取账号和会话当前状态：通过 Spring 代理调用公开方法，采用 `REQUIRES_NEW`。这样，`afterCommit` 回调中的查询可以读取新状态。
4. 账号状态异常、令牌过期、角色或医生绑定变化时，终止业务帧发送并关闭该连接。关闭使用现有 `POLICY_VIOLATION`，连接注销和医生在线状态沿用现有关闭回调。
5. 清退无效连接时直接关闭，防止“发送错误帧 → 再校验 → 再发送错误帧”的递归。
6. 保留现有入站帧和握手校验。

发送入口按帧用途区分：

| 帧 | 发送前检查 |
|---|---|
| `READY`、`PONG`、普通 `ERROR` | 接收方账号与令牌有效 |
| `HISTORY`、`MSG`、`ACK`、`READ`、`PRESENCE`、`SESSION`、`MESSAGE_VISIBILITY` | 账号有效；接收方仍是会话所属主人或医生；会话处置状态正常 |
| `MODERATION` | 账号有效；接收方是原参与方；仅发送会话 ID 与处置状态等通知字段 |

所有携带会话业务内容的发送调用显式传入 `sessionId`，包含正文位于 `message` 内的 `MSG` 与 `ACK`。

正常结束的会话继续允许历史查询、已读和已提交消息的回执。会话处置状态与诊疗状态分别判断。

依赖方向固定为：`ConsultService → ConsultPush → ConsultDeliveryGuard → AccountGuard/Mapper`；Handler 调用 Service 和 Push。Guard 直接使用 Mapper，避免与 Service 形成循环依赖。

### 1.2 清退被处置会话的订阅，修复 F2

1. 在 `ConsultSocketRegistry` 增加按会话移除订阅的方法，从各连接的 `rooms` 集合移除该会话，保留连接上的其他房间。
2. 在 `ConsultPush` 增加明确的处置通知入口：事务提交后，先向原订阅连接发送 `MODERATION`，随后清除该房间订阅。清除动作放入 `finally`，单连接发送异常也应完成清退。
3. `moderate` 的非零处置使用该入口。撤销处置后，由参与方重新订阅恢复后续通知。
4. `changeMessageHidden` 的恢复正文经过统一的会话准入检查；管理员审计查询保持原有权限。
5. `join` 在处理订阅请求时先执行当前成员和处置校验，再判断是否已经登记该房间。
6. 保留现有 `afterCommit` 推送时机。事务回滚时，处置通知与订阅清退均不执行。

### 验收

- **F1 停用场景：** 主人静默保持旧连接；管理员停用账号后医生发送消息。旧连接收到的新业务内容为 0，重连返回 HTTP 401。
- **F1 到期场景：** 使用 2 秒令牌，等待过期后由合法对端发送消息。过期连接收到的新业务内容为 0。
- **F1 双出口：** 分别验证 WebSocket `CHAT` 广播、REST 结束会话通知和恢复消息通知；正常账号的对应操作成功。
- **F2 场景：** 消息先屏蔽 → 主人进入 → 整场会话处置 → 管理员恢复消息。原连接收到处置通知，随后收到的恢复正文为 0；管理员审计查询仍可读取消息。
- 清退一个房间后，同一连接的其他合法房间仍可收发。正常结束会话仍可查看历史。
- 在处置事务回滚的夹具中，确认没有发送处置成功通知，也没有清退原订阅。

原始复现脚本：[verify.mjs](verify.mjs)、[moderation.mjs](moderation.mjs)。实施时将脚本改成上述修复后断言，保留原审计副本。

## 三、步骤 2：按会话串行化写操作，修复 F3

### 修改文件

- [ConsultSessionMapper.java](../../../../backend/src/main/java/com/petclinic/mapper/ConsultSessionMapper.java)：增加会话行锁查询。
- [ConsultService.java](../../../../backend/src/main/java/com/petclinic/service/ConsultService.java)：调整写方法的读取与锁顺序。

### 执行动作

1. 新增 `selectByIdForUpdate(Long sessionId)`：

   ```sql
   SELECT * FROM consult_session WHERE id = #{sessionId} FOR UPDATE
   ```

2. 将成员校验拆成“读取会话”和“验证传入会话的归属及处置状态”。读接口使用普通读取；写接口先取得锁读结果，再验证该结果。
3. `send`、`accept`、`close` 进入事务后先锁会话。状态判断、消息插入、状态更新、摘要更新均使用锁内状态。
4. `moderate` 进入事务后先锁会话，再判断是否需要连带关闭；保持管理员处置权限与留痕字段。
5. 同步调整以下两个已有写入口，统一锁顺序为 **会话行 → 消息行**：
   - `markRead`：先锁会话并校验成员，再执行 `unreadPeerIdsForUpdate` 和已读更新。
   - `changeMessageHidden`：先普通读取消息以取得所属会话 ID，再锁会话，随后更新消息和会话聚合。需要重新读取消息状态时使用当前读。
6. `systemMessage`、`refreshSessionAggregates` 由持有会话行锁的事务调用。检查全部调用点，确认锁覆盖到末次摘要写入。
7. 保留原事务边界、事务提交后推送及消息 ID。前端继续按消息 ID 合并历史与实时消息。

`markRead` 当前会先锁消息；与新增的“先锁会话再写消息”交错会形成相反锁顺序，因此它属于本次必要修改范围。

### 验收

使用原 F3 的两请求行锁夹具，分别安排两种顺序：

| 取得会话锁的顺序 | 应有结果 |
|---|---|
| 关闭先取得锁 | 关闭成功；发送在锁内读到已关闭，返回错误，用户消息落库数为 0 |
| 发送先取得锁 | 用户消息提交成功；关闭随后成功，结束提示成为最后一条消息，摘要与其一致 |

同时记录消息 ID、数据库状态、摘要和帧到达时间。消息提交结果与网络帧到达顺序分别核验。

补充三组双请求检查：发送与已读、发送与屏蔽、已读与屏蔽。断言没有死锁、未读数与可见未读消息数量一致、摘要指向最后一条可见消息。串行关闭后继续发送应返回错误。
