# 主流程测试用例

设计日期：2026-10-21。共 40 组用例，当前状态均为「待执行」。一组中的多个输入或身份分别记录结果。

2026-10-21 主流程测试实际触达的子项及证据见 `docs/test-evidence/20261021/main-flow/测试报告.md` 第 4.2 节；部分子项通过不改变整组状态。

目标：验证宠物主人和医生能走完到院诊疗、图文问诊，并检查号源、支付、病历、消息和权限在异常操作后是否仍然一致。

## 1. 测试基准

以当前工作区的领域约定、服务实现和页面行为作为设计依据。执行时记录 Git 提交号及未提交差异；当前 `ConsultPanel.vue`、医生问诊页等存在未提交修改，测试构建应包含执行时确认的版本。

| 规则 | 当前依据 |
| --- | --- |

## 2. 环境与数据

执行环境使用 `tools/qa_env.py` 管理：独立 MySQL 3307、后端 8082、`yuzhua_test_<8位十六进制>` 测试库及受限账号。前端请求与 WebSocket 均指向该后端；先执行环境检查，再准备数据。建库按工具的 `prepare` 流程处理。

| 代号 | 准备内容 |
| --- | --- |
| U1、U2 | 两个宠物主人；分别拥有 P1、P2；另建一只属于 U1 的 P3 |
| D1、D2、A1 | 两名医生及各自绑定的后台账号；一个管理员账号。医生 ID 与后台账号 ID 使用不同数值 |
| S1 | D1 当天尚未结束的有效排班，容量 3；记录初始余量 R、最后排队序号 Q |
| S2 | D1 独立排班，容量 1，供最后一个号的竞争测试 |
| S3、S4 | 已停诊排班、已结束排班；另准备 D2 排班用于归属篡改 |
| T | 后端实际支付超时配置；记录服务器业务日期和时区 |
| 消息与图片 | 一张可上传图片；含唯一标识的文本；1000/1001 字文本；500/501 字建议与小结；至少 65 条历史消息 |

每组用例使用独立记录；需要多个终态时分别建单。并发用例以屏障同时释放请求，建议每个交错场景重复 20 轮，逐轮重置数据。精确时间边界采用受控时钟；测试框架暂不支持时，记录该子项为待执行。超时清扫通过实际任务入口或测试夹具调用真实服务方法。

## 3. 完整流程（P0）

### E01 到院诊疗闭环

前置：U1、P1、D1、S1 可用，记录 R 与医生已完成接诊数 N。

1. U1 登录，从医生详情选择 S1、P1，填写症状并提交预约。
2. 查看预约详情，完成模拟支付；刷新页面，核对支付状态和凭证。
3. D1 登录，在预约列表打开该预约并接诊。
4. D1 填写诊断、治疗建议，保存病历，然后结束就诊。
5. U1 打开病历详情，提交 5 星评价，再查看预约和医生评价列表。

预期：每步页面均可继续操作；预约最终已完成、已支付、已评价；余量为 R−1；有效病历和评价各 1 条；医生已完成接诊数为 N+1；病历日期等于预约日期。刷新及重新登录后，列表、详情、数据库的状态一致。

### E02 图文问诊闭环

前置：U1、P1、D1 可用；记录预约数 B、各排班余量；两端使用独立浏览器上下文。

1. U1 从医生详情发起问诊，填写症状并进入会话。
2. U1 在待接诊阶段发送补充说明；D1 打开会话并接诊。
3. 双方分别发送文字和图片；D1 发送一条建议到院消息。
4. D1 填写就诊小结并结束；双方刷新，重新打开历史会话。

预期：正文、图片、发送方、顺序正确；双方状态更新为已结束，小结保留；结束后输入区与状态一致；历史可读；预约数始终为 B，各排班余量保持原值，问诊期间新增病历数为 0。
