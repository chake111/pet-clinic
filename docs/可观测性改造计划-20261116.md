## 现状

先把已有部分说清楚，避免把“接 healthcheck”当成从零开始。

- Actuator 依赖已经在 `backend/pom.xml:41-44`。`application.yml:56-63` 只暴露 `health`，`show-details: never`；服务端口 8081，context-path 是 `/api`。
- Compose 的 backend healthcheck 已经在 curl `/api/actuator/health`（`compose.yaml:56-61`），CI 也通过 nginx 检查同一路径（`.github/workflows/docker.yml:40`）。这次要做的是把“进程活着”和“能对外服务”分开，不是重新接一遍。
- 没有 Prometheus registry，也没有 `metrics` / `prometheus` 端点。`micrometer-core` 随 actuator 进来，但指标只留在内存里，没有出口。
- 没有慢 SQL 计时。`mybatis-plus.configuration.log-impl` 仍是注释状态（`application.yml:38-39`）；打开它只能看到 SQL 文本，没有耗时，也没有 traceId。
- 现有 k6 是并发正确性测试：100 VU、每人 1 次（`tools/load/booking-race.js:37-42`）。README 里 race 的 p95 是 100 个写事务被行锁串行化后的整批耗时，不是稳态吞吐。QPS、错误率和面板截图都还没有。
- `deploy/` 下只有 nginx 和 web，没有 Prometheus/Grafana。

## 目标

1. Compose 用 readiness 判断 backend：readiness 包含 `db`，数据库不可用时返回 503；liveness 只看进程。停库、恢复各验证一次。
2. Docker 网络内可抓取 `/api/actuator/prometheus`，包含 `http_server_requests_seconds_count` 和 `_bucket`，能算 QPS、p95、5xx 比例。
3. 超过阈值的 MyBatis 语句打 WARN，带 statement id、耗时；traceId 由现有日志 pattern 带出，不带参数；阈值可配置，有单测。
4. 3 分钟稳态读混合压测，k6 summary 与 Grafana 截图进入 README；数值、口径、环境一起写。

## 不做什么

- 不接 Micrometer Tracing / Tempo / Loki / Alertmanager。单实例单库，没有跨服务调用要串；上一轮 H4 已经因为成本否决过整套 tracing（`docs/技术亮点改造记录-20261114.md:300`）。
- 不引入 p6spy / datasource-proxy。业务 SQL 全走 MyBatis，一个 `Interceptor` 能覆盖；JDBC 代理多一层开销，还要多一个依赖。
- 不改业务 SQL，不动索引。慢 SQL 这轮只负责“看得见”，优化另开任务。
- 不单独开 management 端口。8081 没有发布到宿主机，actuator 对外只放 health，metrics/prometheus 在 nginx 层返回 404。以后要独立管理端口，再一起改 compose、CI 和部署文档。
- 不把 Prometheus/Grafana 放进默认 compose。用 `observability` profile，`docker compose up` 仍然是三个服务。
- 前端不改；nginx 只加两条 404 规则。

## 2. Actuator 健康分组（0.75h）

`backend/src/main/resources/application.yml` 的 `management` 段改成：

```yaml
management:
  endpoint:
    health:
      show-details: never
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,db
```

`compose.yaml` 的 backend healthcheck 从完整 health 改成 readiness：

```yaml
healthcheck:
  test: ["CMD", "curl", "-fsS", "http://127.0.0.1:8081/api/actuator/health/readiness"]
```

`probes.enabled` 不能省：Spring Boot 只在 Kubernetes 环境下自动开启 liveness/readiness，Docker Compose 不会。readiness 显式包含 `db`，否则默认分组只看 `readinessState`，数据库挂了也会报 UP。

验证：

```bash
docker compose up -d --build --wait
curl -fsS http://127.0.0.1:8088/api/actuator/health/readiness
curl -fsS http://127.0.0.1:8088/api/actuator/health/liveness

docker compose stop db
# Hikari connection-timeout 是 10s，等 10–15s 再查
curl -i http://127.0.0.1:8088/api/actuator/health/readiness   # 503
curl -i http://127.0.0.1:8088/api/actuator/health/liveness    # 200

docker compose start db
# 等 db 健康、backend readiness 回到 200
```

验收：

- readiness 和 liveness 都返回 200。
- 停 db 后 readiness 返回 503，liveness 仍是 200；启 db 后 readiness 恢复 200。
- `docker compose ps` 里 backend 重新变为 healthy。

注意：停库验证会打断正在使用演示环境的人。操作前确认没有人在走流程；验证完立刻把 db 启回来。

## 3. Micrometer 指标出口（0.75h）

`backend/pom.xml` 增加 registry，版本由 Spring Boot BOM 管理，不写版本号：

```xml
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

`application.yml` 的 `management` 段补齐：

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,metrics,prometheus
  endpoint:
    health:
      show-details: never
      probes:
        enabled: true
      group:
        readiness:
          include: readinessState,db
  metrics:
    tags:
      application: ${spring.application.name}
    distribution:
      percentiles-histogram:
        http.server.requests: true
      percentiles:
        http.server.requests: 0.5,0.95,0.99
```

`percentiles-histogram` 是给 Prometheus 算 `histogram_quantile` 用的；`percentiles` 让 `/actuator/metrics` 直接显示分位数，方便命令行核对。两者都开，单实例压测开销可以忽略。

`deploy/nginx/default.conf` 在 `location /api/` 之前加两条，只在 nginx 层挡住指标端点：

```nginx
location /api/actuator/metrics { return 404; }
location /api/actuator/prometheus { return 404; }
```

Prometheus 容器直接访问 `backend:8081`，不经过 nginx，所以抓取不受影响。health 仍然可以经 nginx 访问，CI 现有检查不用改。

验证：

```bash
# 先制造一点流量，空闲实例不会凭空出现 http.server.requests
for i in $(seq 1 20); do
  curl -fsS http://127.0.0.1:8088/api/client/catalog/home >/dev/null
done

# compose 没有发布 8081，用 exec 在容器内查
docker compose exec -T backend \
  curl -fsS http://127.0.0.1:8081/api/actuator/metrics/http.server.requests

docker compose exec -T backend sh -c \
  "curl -fsS http://127.0.0.1:8081/api/actuator/prometheus | grep '^http_server_requests_seconds' | head"

# 外部应被 nginx 挡住
curl -s -o /dev/null -w '%{http_code}\n' \
  http://127.0.0.1:8088/api/actuator/prometheus   # 404
```

验收：

- `http_server_requests_seconds_count`、`_sum`、`_bucket` 出现。
- 标签里有 `application`、`method`、`uri`、`status`、`outcome`。把 `uri` 的实际取值记下来，PromQL 不靠猜。
- `/api/actuator/prometheus` 从宿主机经 nginx 返回 404；容器网络内可抓取。

## 4. 慢 SQL（1.5h）

### 4.1 配置项

`backend/src/main/java/com/petclinic/config/AppProperties.java` 增加嵌套配置：

```java
@Valid
private Observability observability = new Observability();

@Data
public static class Observability {
    /** 超过该毫秒数的 MyBatis 语句打 WARN；0 表示关闭 */
    @Min(value = 0, message = "慢 SQL 阈值不能为负数")
    private long slowSqlThresholdMs = 200;
}
```

`application.yml` 的 `petclinic` 段补：

```yaml
petclinic:
  observability:
    slow-sql-threshold-ms: 200
```

### 4.2 拦截器

新增 `backend/src/main/java/com/petclinic/config/SlowSqlInterceptor.java`：

- 实现 MyBatis `Interceptor`，用 `@Intercepts` 拦 `Executor.query`（4 参）和 `Executor.update`。
- `@Component` 注册。MyBatis-Plus 的自动配置会收集容器里的 `Interceptor` bean，不需要再改 `MybatisPlusConfig`。
- 用 `System.nanoTime()` 计时，`finally` 里判断阈值；异常路径也记录耗时，但只记 `failed=true`，不记异常消息。
- 日志字段：`statement`（`MappedStatement.getId()`）、`type`（`getSqlCommandType()`）、`elapsed`、`failed`。traceId 由现有日志 pattern（`application.yml:89-92` 的 `%X{traceId:-}`）带出，不重复写进消息。
- 不记录 SQL 文本和参数。手机号、症状、病历内容都可能出现在参数里；statement id 足够定位到 mapper 方法。

日志形如：

```text
WARN [3f2a...] c.p.c.SlowSqlInterceptor - 慢 SQL statement=com.petclinic.mapper.AppointmentMapper.updateRemain type=UPDATE elapsed=1243ms failed=false
```

计时的边界要说清楚：它包住的是 MyBatis `Executor` 调用，可能包含行锁等待、分页的 count/分页查询和结果映射，具体取决于插件顺序；不是纯 MySQL 执行时间。压测时 100 个写事务抢同一行，慢 SQL 日志里会出现秒级耗时；这是行锁排队，不是 SQL 写法突然变差。README 引用时按这个口径写。

不接 MySQL 自带 slow log 的原因：慢日志在容器里，没有 traceId，和某一次请求对不上；应用层日志的 traceId 由 MDC pattern 带出，能和请求对上。以后要看纯 DB 执行时间，再单独开 MySQL slow log 做对照。

### 4.3 单测

新增 `backend/src/test/java/com/petclinic/config/SlowSqlInterceptorTest.java`，用 `OutputCaptureExtension` 捕获日志，Mockito mock `Invocation` 和 `MappedStatement`，固定纳秒时钟，不 sleep。

覆盖：

- 低于阈值不打日志。
- 达到或超过阈值打 WARN，包含 statement id、elapsed、failed。
- 阈值 0 关闭。
- 被拦截方法抛异常时原样抛出，且慢调用仍然记录 `failed=true`。
- 日志里不出现参数值。

单测不启动 Spring 上下文，`application.yml` 里的日志 pattern 不会生效，所以 traceId 不放进断言；它由运行期 pattern 带出，在 4.4 的真实压测日志里核对。

`AppPropertiesValidationTest` 补一条：`slowSqlThresholdMs = -1` 时校验失败，0 和 200 合法。

### 4.4 压测触发与证据

现有 `tools/load/run-load.sh` 的 `EVIDENCE_DIR` 是写死的。把第 24 行改成可覆盖：

然后用 100 VU race 触发行锁等待，把日志过滤到新证据目录，不覆盖 11-16 已有的集成测试证据：

验收：

- `slow-sql.log` 至少有一行；没有参数值，只有 statement id、耗时，traceId 由日志 pattern 带出。

## 5. Prometheus + Grafana（1.5h）

用 compose profile，默认栈不受影响。镜像固定具体 tag，不用 `latest`；实施时按 Docker Hub 当前稳定版写死，并把 tag 记进 `env.txt`。

`compose.yaml` 增加：

```yaml
  prometheus:
    image: prom/prometheus:<pinned>
    profiles: ["observability"]
    command:
      - --config.file=/etc/prometheus/prometheus.yml
    volumes:
      - ./deploy/observability/prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:${PETCLINIC_PROM_PORT:-9090}:9090"
    depends_on:
      - backend
    security_opt:
      - no-new-privileges:true
    logging: *default-logging

  grafana:
    image: grafana/grafana:<pinned>
    profiles: ["observability"]
    environment:
      GF_SECURITY_ADMIN_PASSWORD: ${PETCLINIC_GRAFANA_PASSWORD:-admin}
      GF_USERS_ALLOW_SIGN_UP: "false"
    volumes:
      - ./deploy/observability/grafana/provisioning:/etc/grafana/provisioning:ro
      - ./deploy/observability/grafana/dashboards:/var/lib/grafana/dashboards:ro
    ports:
      - "127.0.0.1:${PETCLINIC_GRAFANA_PORT:-3000}:3000"
    depends_on:
      - prometheus
    security_opt:
      - no-new-privileges:true
    logging: *default-logging
```

Prometheus 和 Grafana 只绑定 `127.0.0.1`，不发布到局域网。Grafana 不给命名卷，容器删掉后数据一起清掉；面板和数据源都由文件 provision，不靠手工配置。

`deploy/observability/grafana/provisioning/dashboards/dashboards.yml`：

  - name: pet-clinic
    orgId: 1

    type: file
    disableDeletion: false
    updateIntervalSeconds: 10

`deploy/observability/grafana/dashboards/pet-clinic.json` 放三格面板，时区设 `Asia/Shanghai`：

```promql
# QPS，排除 actuator 自身抓取
sum(rate(http_server_requests_seconds_count{job="pet-clinic-backend",uri!~".*actuator.*"}[1m]))

# p95
histogram_quantile(0.95,
  sum by (le) (
    rate(http_server_requests_seconds_bucket{job="pet-clinic-backend",uri!~".*actuator.*"}[1m])
  )
)

# 5xx 比例，单位 %
100 * sum(rate(http_server_requests_seconds_count{job="pet-clinic-backend",status=~"5..",uri!~".*actuator.*"}[1m]))
    / clamp_min(sum(rate(http_server_requests_seconds_count{job="pet-clinic-backend",uri!~".*actuator.*"}[1m])), 0.0001)
```

`uri` 标签的实际值要先在 `/actuator/metrics/http.server.requests` 里确认：可能是模板路径，也可能带 context-path。上面用 `.*actuator.*` 是故意放宽，确认后可以换成更精确的过滤。不排除 actuator 抓取，QPS 会把自己的 scrape 算进去，数字虚高。

启动与检查：

```bash

  up -d --build --wait db backend prometheus grafana

curl -fsS http://127.0.0.1:9090/-/ready
curl -fsS http://127.0.0.1:3000/api/health
# 浏览器打开 http://127.0.0.1:9090/targets，确认 target UP
```

先用 30 秒、5 VU 的小流量把面板跑出曲线，再进入正式压测。没有流量时 `http.server.requests` 不会出现，别把空面板当成配置失败。

止损线：如果 15:00 前 Grafana 面板还不出数，砍掉 Grafana，保留 Prometheus，用 Prometheus 查询页截图；Micrometer、Prometheus 和慢 SQL 不动。不伪造面板截图。

## 6. 稳态压测与截图（1.5h）

现有 race 是“同一行 100 个写事务”的正确性测试，不能拿来算稳态 QPS。新增一个读混合场景，单独跑。

`tools/load/api-mix.js`：

```js
export const options = {
  scenarios: {
    steady: {
      executor: 'constant-arrival-rate',
      rate: 30,
      timeUnit: '1s',
      duration: '3m',
      preAllocatedVUs: 30,
      maxVUs: 100,
    },
  },
  thresholds: {
    'http_req_failed{phase:steady}': ['rate<0.01'],
    'business_error': ['count==0'],
    'http_req_duration{phase:steady}': ['p(95)<1000'],
    'dropped_iterations': ['count==0'],
  },
};
```

30 req/s 是这次的可重复负载，不是系统上限；README 不要把它写成最大吞吐。`p95<1000` 只是退化护栏，实测值照录，不为了让数字好看放宽阈值。

场景参数用 `__ENV.RATE`、`__ENV.DURATION`、`__ENV.PRE_VUS` 覆盖默认值。smoke 用 `RATE=5 DURATION=30s`，正式跑用上面的默认值；`run-steady.sh` 把最终使用的参数写进日志和证据说明。

请求组合：

| 权重 | 方法 | 路径 | 说明 |
| --- | --- | --- | --- |
| 1 | GET | `/client/catalog/home` | 首页聚合，最重 |
| 2 | GET | `/client/catalog/doctors?pageNum=1&pageSize=10` | 医生列表 |
| 2 | GET | `/client/catalog/doctors/9001/schedules` | 号源列表 |
| 1 | GET | `/client/catalog/notices?pageNum=1&pageSize=10` | 公告列表 |
| 1 | GET | `/client/pet` | 我的宠物，带 token |
| 1 | GET | `/client/appointment/page?pageNum=1&pageSize=10` | 我的预约，带 token |

`setup()` 用 fixture 里的 `itload / 123456` 登录一次。每个请求带 `tags: { phase: 'steady', endpoint: '<name>' }`。响应体 `code != 200` 时给 `business_error` 加一；响应不是 JSON、解析失败也计入 `business_error`，不静默忽略。项目的业务失败在 HTTP 层仍是 200，只看 `http_req_failed` 会把错误率报成 0。

只测读接口的原因：写路径的并发正确性已经由 race/oversell 覆盖；稳态测试要的是固定数据下的吞吐和延迟，混入写操作会让数据持续增长，3 分钟后的数字和 30 秒时的数字不是一个口径。

`tools/load/run-steady.sh`：

- 用独立项目 `petclinicperf`，只启动 `db backend prometheus grafana`，不启动 web，避免和演示栈抢 8088。
- 导入 `fixture.sql`，跑 3 分钟，导出 `summary-steady.json`，日志 tee 到 `docs/test-evidence/20261116-observability/steady.log`。
- 默认保留栈供截图，打印 Grafana 地址和清理命令；`KEEP=0` 时自动 `down -v`。
- 复用 `run-load.sh` 里的 `cygpath` / `MSYS_NO_PATHCONV` 处理，Windows Git Bash 下挂载脚本目录不会踩路径转换。
- 9090/3000 被占用时，通过 compose 变量改宿主机端口，仍然只绑 `127.0.0.1`。

运行：

```bash
bash tools/load/run-steady.sh

# 浏览器打开 http://127.0.0.1:3000
# 选择 pet-clinic 面板，时间范围覆盖压测的 3 分钟
# 截图 1600×900，保存为
# docs/test-evidence/20261116-observability/grafana-steady.png
```

截图前确认 QPS 面板有一段平稳的平台，不是只有启动/结束的尖峰。Grafana 的时间窗口和 k6 运行窗口要对上，否则图和表是两段时间。

数值口径：

- QPS：`summary-steady.json` 里 `http_reqs{phase:steady}` 的 rate。
- p95：`http_req_duration{phase:steady}` 的 `p(95)`，是 k6 客户端观测到的端到端耗时，包含网络和排队；Grafana 的 p95 来自服务端 `http.server.requests`，两者不会完全相等。
- HTTP 错误率：`http_req_failed{phase:steady}` 的 rate。
- 业务错误率：`business_error` 计数 / `http_reqs{phase:steady}` 计数。
- 目标速率是否达到：看 `dropped_iterations`，不为 0 就说明 30 req/s 没打满，本次数字不能按 30 req/s 解读。

交叉核对：把 Prometheus 在同一窗口的平均 QPS 和 k6 的 QPS 对一下。差异超过 10% 先查 `uri` 过滤、抓取间隔和时间窗口，不直接选好看的那个。p95 的两种算法本来就有误差，README 以 k6 summary 为准，Grafana 只用于展示趋势。

验收：

- `dropped_iterations = 0`，`business_error = 0`，HTTP 错误率低于 1%。
- 截图里能看到 3 分钟平台段。
- README 的数字与 `summary-steady.json` 一致，没有手填的“大概值”。

## 风险与应对

| 风险 | 表现 | 应对 |
| --- | --- | --- |
| 9090/3000 被占用 | compose 起不来 | 先 `netstat -ano \| findstr` 查端口，用变量改宿主机端口，仍绑 `127.0.0.1` |
| Grafana provisioning 失败 | 面板空白、数据源未加载 | 看 `docker compose logs grafana`；校验 YAML 缩进；超时就走 Prometheus 截图止损线 |
| 空闲实例没有指标 | `/actuator/prometheus` 里没有 `http_server_requests` | 先发请求；指标只在有流量后出现 |
| k6 目标速率打不满 | `dropped_iterations > 0` | 记录实际速率，查 VU 和响应时间；不把未达标的数字写成 30 req/s |
| 慢 SQL 不触发 | `slow-sql.log` 为空 | 降到 100ms 重跑并记录阈值；仍为空则查拦截器是否注册、语句是否走 MyBatis |
| 指标端点外泄 | 公网能访问 `/api/actuator/prometheus` | nginx 两条 404；CI 断言；8081 不发布到宿主机 |
| 健康检查抖动 | 启动时反复 unhealthy | readiness 含 db，db 已有 healthcheck 且 `depends_on` 先等 db；`start_period: 60s` 保留 |
| 证据被覆盖 | 旧的 race 日志被新跑覆盖 | 新目录 + `EVIDENCE_DIR` 覆盖；复跑新建日期目录 |
| Windows 路径转换 | k6 容器挂载不到脚本 | 复用 `cygpath` 与 `MSYS_NO_PATHCONV=1`，不要另写一套 |
