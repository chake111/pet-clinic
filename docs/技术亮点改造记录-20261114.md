# 四条技术亮点改造记录（2026-11-14）

四条改造各自独立完成、独立验证后合并；下面保留缺陷、动作与证据。

四条覆盖四个不同方向，根因互不重叠：

| 编号 | 方向 | 一句话不变量 |
| --- | --- | --- |
| H1 | 并发写入的正确性 | 排班的停诊位只能由 `/stop`、`/resume` 写，编辑接口碰不到它 |
| H2 | 实时通道的语义 | 已读只由「人看见了」触发，不由「连接建立了」触发 |
| H3 | 数据访问 | 看板今日五格一次往返取回，且按日期取数走索引 |
| H4 | 交付与可观测 | 每一次失败都能从用户拿到的提示回溯到那一行日志 |

其中 H1、H3 都是减法：H1 从编辑契约里删掉一个字段，H3 删掉 4 条查询和 2 个方法。

## H1 停诊被旧表单覆盖

### 缺陷

`PUT /admin/schedule/{id}` 的请求体带着 `status`，`/stop`、`/resume` 也写同一个列。
一个停留在停诊之前的编辑弹窗再保存一次，就把期间执行的停诊静默撤销了。
是一次典型的丢失更新：后到的写覆盖了先到的写，而两个写都是"合法"的。

### 不变量

排班的 `status` 列只有一个写入面：`stopClinic` / `resumeClinic`。
编辑路径不写这一列——不是"写了等于原值"，而是压根不接受这个字段。

### 证据

- 契约：[`ScheduleEditForm.java`](../backend/src/main/java/com/yuzhua/dto/ScheduleEditForm.java) 六个字段，无 `status`
- 入口：[`ScheduleController.java:66`](../backend/src/main/java/com/yuzhua/controller/admin/ScheduleController.java) 收 `ScheduleEditForm`
- 写入点：[`DoctorScheduleService.java:141`](../backend/src/main/java/com/yuzhua/service/DoctorScheduleService.java) 签名已换；`:202` 明确不 `setStatus`
- 前端：[`Schedules.vue`](../frontend/src/views/admin/Schedules.vue) 编辑弹窗不再渲染状态单选，提交体显式只带六个字段

### 命令与输出原文

改前（隔离库，排班 684）：

```
1) 停诊：
{"code":200,"msg":"已停诊"}
   库里 status = 0
2) 模拟一个停留在停诊之前的编辑弹窗，点保存：
{"code":200,"msg":"已保存"}
   库里 status = 1  <-- 停诊被旧表单静默撤销
```

改后，同一条请求，请求体里**故意**塞 `"status":1`（最终集成构建上的原始输出）：

```
### H1 (排班 684)
  停诊后 status=0
  陈旧表单带 status:1 保存后 status=0  total_num=24
```

停诊位保持 0，而同一请求里的号源数照样写进去了（24）——说明不是"整条请求被忽略"，
而是只有状态这一列不在写入范围内。恢复走专用接口后 `status=1`。

### 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 保留字段，服务层强制写 `cur.getStatus()` | 字段还在契约里，前端传什么都静默无效。下一个改这块的人看表单有 `status` 就会以为能改，同类缺陷会再来一次 |
| 加乐观锁（版本号 / `update_time` 比对） | 能挡住覆盖，但代价是编辑接口多一个必填版本号，所有调用方都要改；而这里根本不需要"允许改状态"这个能力，删掉字段是更小的手术 |
| 前端只读展示，后端照旧接收 | 换一个客户端（脚本、Swagger）就能绕过。拦截点必须在服务端类型上 |

### 回滚

`git revert 89f102e`。回滚后编辑接口重新接收 `status`，旧弹窗覆盖停诊的行为恢复；
数据库无需任何动作（本改造不含 DDL）。

## H2 重连即全量已读

### 缺陷

`subscribe`（含 WebSocket 握手自动进房）无条件调 `markRead`。刷新页面、断线重连、
手机锁屏解锁都会重新进房，于是「重连一次 = 把对侧消息全部标成已读」。
未读红点在没有任何人查看的情况下消失——对医生侧尤其严重，等于漏掉患者的消息。

### 不变量

已读是一个事实（有人看见了），不是一个事件（连接建立了）。
服务端只认上行 `READ` 帧；客户端只在「页面可见 ∧ 历史已渲染」时发。

### 证据

- 服务端：[`ConsultWebSocketHandler.java:162`](../backend/src/main/java/com/yuzhua/websocket/ConsultWebSocketHandler.java) `subscribe` 的注释与实现，只补 `HISTORY` 与 `PRESENCE`
- 客户端：[`ConsultPanel.vue:69`](../frontend/src/components/ConsultPanel.vue) `pageVisible`；`:89` `markReadIfSeen` 是唯一的发帧判据
- 可见性监听：`visibilitychange` 切回前台补一次

### 命令与输出原文

取证实脚本 `.tmp/qa/evidence-h2.mjs`：只建连、只收帧、**不发任何 READ 帧**。

改前（会话 4，医生已发 1 条）：

```
连接前  {"userUnread":"1","doctorUnread":"0","unreadMessages":"1","readMessages":"0"}
收到帧  ["READY","HISTORY","PRESENCE"]
未发 READ 帧，仅重连后  {"userUnread":"0","doctorUnread":"0","unreadMessages":"0","readMessages":"1"}
```

改后（会话 224）：

```
连接前  {"userUnread":"1","doctorUnread":"0","unreadMessages":"1","readMessages":"0"}
收到帧  ["READY","HISTORY","PRESENCE"]
未发 READ 帧，仅重连后  {"userUnread":"1","doctorUnread":"0","unreadMessages":"1","readMessages":"0"}
```

显式发 `READ` 帧之后才归零（同一条命令，把 `READ` 补上）：

```
收到帧: READY HISTORY PRESENCE
user_unread / 未读消息数 = 0 / 0
```

### 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 服务端只保留 REST 已读接口，删掉 WS 的 `READ` | 聊天页每次已读都要走一次 HTTP，收到消息的高频场景下多一轮往返；且 WS 通道已经在了，加个帧比加个请求轻 |
| 加"可见"参数随 `SUBSCRIBE` 上报，服务端据此决定标不标 | 客户端可以撒谎，等于把权限判断交给前端；而且断线重连时前端自己也不知道当时是否可见 |
| 延迟 N 秒后再标已读 | 治标：延迟窗口内页面可能仍不可见（后台标签页），问题原样存在，只是概率变小 |

### 回滚

`git revert bdb21c5`。无 DDL。回滚后需同步回退前端：新前端只在可见时发 `READ`，
旧后端在进房时自行标已读，两者并存不会报错，但重连误标已读的行为会回来。

## H3 看板 5 条全表扫

### 缺陷

看板一次请求要取「今天」的总单量、分流三态、营收，原先是 4 次 `COUNT` + 1 次 `SUM`，
五条语句在同一批行上做五遍相同过滤。且全院口径（`doctorId` 为 NULL 不过滤）下
`appointment_date` 无可用索引——`idx_status` 只含 `status` 一列，
`idx_doctor_date` 前导列是 `doctor_id`，两条都用不上。

### 不变量

今日五格来自一次条件聚合；口径与逐条写法逐项等价。按就诊日期取数的查询能命中索引。

### 证据

- SQL：[`AppointmentMapper.java:129`](../backend/src/main/java/com/yuzhua/mapper/AppointmentMapper.java) `todayCard`
- 调用：[`StatsService.java:52`](../backend/src/main/java/com/yuzhua/service/StatsService.java)；`countToday` 与 `sumTodayIncome` 已删除，不留零调用方的旧口径
- 索引：`sql/01_schema.sql:225`，迁移 [`sql/migrations/20261114_add_appointment_visit_date_index.sql`](../sql/migrations/20261114_add_appointment_visit_date_index.sql)

### 命令与输出原文

测量方法：`SHOW GLOBAL STATUS LIKE 'Com_select'` 前后取差，再扣掉读计数器本身的 1 次。

```
a=$(SHOW GLOBAL STATUS LIKE 'Com_select')
curl -s -o /dev/null -H "Authorization: Bearer $T" .../admin/stats/dashboard?days=14
b=$(SHOW GLOBAL STATUS LIKE 'Com_select')
单次增量 = b - a - 1
```

改前（隔离库 103 行数据集）：

```
单次看板请求的 SELECT 增量 = 17
  （18 - 1：其中 5 次是今日五格，其余为鉴权回查与四组图表聚合）

今日五格的执行计划：
no-status                    => type=ALL  key=NULL          rows=103  Extra=Using where
status=0                     => type=ref  key=idx_status    rows=2    Extra=Using where
status=1                     => type=ref  key=idx_status    rows=1    Extra=Using where
status=2                     => type=ref  key=idx_status    rows=86   Extra=Using where
pay_status=1                 => type=ALL  key=NULL          rows=103  Extra=Using where
```

改后（同一实例、同一数据集，连续复测 3 次都是 13）：

```
单次看板请求的 SELECT 增量 = 13

合并后的今日五格   type=ref  key=idx_visit_date  rows=2
医生视角 doctor_id=1     type=ref  key=idx_doctor_date  rows=1
```

每条请求少 4 次 SELECT（今日五格 5 → 1）；两条 `type=ALL rows=103` 变成 `type=ref rows=2`。
医生视角继续走已有的 `idx_doctor_date`，新索引没有取代它。

> 早先草稿里还写过"5 次请求合计 86 → 66"，那组数字把读计数器的语句也算进去了，
> 与"每条 17/13"差 1，属于统计口径写错，已删掉——保留单次增量这一个口径。

口径等价核对（两种口径各比五项）：

```
--- doctorId=NULL ---
  旧 5 条: 2/2/0/0/70.00
  新 1 条: 2/2/0/0/70.00
  一致
--- doctorId=1 ---
  旧 5 条: 0/0/0/0/0.00
  新 1 条: 0/0/0/0/0.00
  一致
```

### 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 只加索引，不改 5 条查询 | 索引能让每条变快，但往返次数不变，仍是 5 次；5 次扫一遍变成 5 次走索引，收益上限被往返卡住 |
| 只合成 1 条查询，不加索引 | 往返降了，但仍全表扫。当前 103 行看不出差别，数据量上去后单条也会慢 |
| 加 `(appointment_date, pay_status)` 第二个索引 | 合成单条后只剩 `appointment_date` 一个等值条件，第二个索引用不上；多一个索引就多一份写入成本 |
| 把今日数字缓存 / 物化到统计表 | 需要引入缓存失效逻辑，而这次改动的量级（一条 SQL + 一个索引）已经够；缓存属于"为了简历加中间件"，本项目的约束明确排除了 |

### 回滚

```sql
DROP INDEX idx_visit_date ON appointment;
```

再 `git revert ed72a7c`（恢复 5 条查询）。索引与代码可独立回滚：
只删索引不会让功能出错，只回代码也不会（新查询不依赖索引，只是变慢）。

## H4 无 traceId 导致 500 无法定位

### 缺陷

兜底异常只记 uri。同一个接口反复失败时，日志里是一串一模一样的行；
用户截图里的「服务器繁忙，请稍后再试」没法对应到具体哪一次请求。

### 不变量

任何一个 500 都能从用户拿到的字符串回溯到唯一一行日志，且该号也出现在响应头里。

### 证据

- [`TraceIdFilter.java`](../backend/src/main/java/com/yuzhua/common/TraceIdFilter.java)：`HIGHEST_PRECEDENCE`，MDC + `X-Trace-Id`，`finally` 清 MDC
- [`GlobalExceptionHandler.java:108`](../backend/src/main/java/com/yuzhua/common/GlobalExceptionHandler.java)：记 traceId/method/uri，响应 msg 回显
- `application.yml`：`logging.pattern.level: "%5p [%X{traceId:-}]"`
- 测试：[`TraceIdFilterTest.java`](../backend/src/test/java/com/yuzhua/common/TraceIdFilterTest.java) 5 例

### 命令与输出原文

改前：

```
响应：{"code":500,"msg":"服务器繁忙，请稍后再试"}
响应头（找关联 id）：没有任何关联 id 响应头
日志：ERROR ... 系统异常 uri=/api/admin/user/abc
```

改后，同一请求：

```
{"code":500,"msg":"服务器繁忙，请稍后再试（追踪号 9d47a390ecb540fba0328bacf05658a0）"}
X-Trace-Id: 9d47a390ecb540fba0328bacf05658a0
```

用这个号 grep，能拉到同一次请求的全部日志（含鉴权回查与 DEBUG SQL）与堆栈：

```
ERROR [9d47a390…] ... 系统异常 traceId=9d47a390… method=GET u…
DEBUG [9d47a390…] ... AdminUserMapper.selectById : ==>  Preparing: SELECT …
DEBUG [9d47a390…] ... AdminUserMapper.selectById : <==      Total: 1
ERROR [9d47a390…] ... 系统异常 traceId=9d47a390… method=GET u…
```

入站头与防日志注入。白名单只认本系统自己生成的形状（32 位小写 hex）：
`/client/**` 与 `/admin/auth/login` 都匿名可达，泛化白名单等于允许任意客户端
指定固定号把多条请求的日志并成一条。

```
请求头 X-Trace-Id: 9d47a390ecb540fba0328bacf05658a0
  → 响应 {"code":500,"msg":"…（追踪号 9d47a390…）"}
  → X-Trace-Id: 9d47a390…               （形状合法，沿用）

请求头 X-Trace-Id: gateway-abc-12345
  → X-Trace-Id: 14c0549c0ddd40d6a641239c8900de82   （自定义前缀，换新号）
请求头 X-Trace-Id: 00-4bf92f35…-b7-01     （W3C traceparent）
  → 换新号
请求头 X-Trace-Id: AAAAAAAA               （匿名固定值）
  → 换新号
请求头 X-Trace-Id: xxxxx…（200 位）        （超长）
  → 换新号
```

代价：放弃了"上游网关自定义前缀"的串联能力。本系统没有跨服务调用，这个交换划得来；
将来真接了网关，用显式前缀白名单（如 `^gw-[0-9a-f]{32}$`）再放开。

### 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 引入 Micrometer Tracing / Sleuth | 为「一个号」拉进一整套链路追踪。当前是单实例单库，没有跨服务调用要串，成本远大于收益 |
| 用请求 id（`request.getRequestId()`） | Tomcat 的 request id 只活在容器里，不进 MDC，日志行上拿不到，等于没解决 |
| 只用 MDC 不上响应头 | 用户看不到号，报障时说不出来，整条链路断在第一步 |
| 把堆栈直接回给前端 | 泄漏内部结构（表名、包名、SQL）。追踪号是随机串，不含业务信息，才敢外露 |

### 回滚

`git revert a4dd65e`。无 DDL。回滚后 500 响应恢复成固定文案，日志去掉 `[traceId]` 前缀。

## 简历条目（每条不超过两行，数字均可回溯到上文的命令）

- **排班状态双写修复**：发现编辑接口与停诊接口写同一状态列导致的丢失更新，把 `status` 从编辑契约里删除，
  状态只由专用端点写入；陈旧表单携带旧值再提交时停诊保持不变（改前 0→1，改后 0→0）。
- **问诊已读语义修正**：定位到 WebSocket 进房即 `markRead` 的缺陷，改为仅由显式已读帧触发、
  且前端在页面可见时发送；断线重连后未读数保持 1（改前被误清为 0）。
- **看板查询合并与索引优化**：今日五项指标由 5 条独立聚合合成 1 条条件聚合，单次看板请求的 SELECT
  由 17 降为 13；补 `appointment_date` 索引后执行计划由 `type=ALL rows=103` 变为 `type=ref rows=2`。
- **请求级追踪号**：为每个 HTTP 请求生成 traceId，同时写入 `X-Trace-Id` 响应头、500 提示文案与全部日志行，
  用户报障可用该号一次 grep 定位到那一次请求的完整堆栈。

## 追问准备

**H1**
1. *为什么不用乐观锁？* 乐观锁要全链路传版本号，而这个接口本来就不需要"改状态"这个能力；
   删字段是把错误的能力收回去，比给错误的能力加保护更彻底。
2. *边界在哪？* 只挡住经 HTTP 的编辑。直连数据库改这一列不受保护（任何应用层校验都挡不住 DBA）；
   多实例部署时也不需要额外协调，因为写入面只剩两个幂等的单行 UPDATE。
3. *挂了怎么办？* 前端如果漏改（仍发 `status`），Jackson 默认忽略未知字段，接口照常返回 200，
   只是这个字段无效——不会 400 打断保存。

**H2**
1. *为什么不用 visibility API 之前先不发已读？* 就是不发。已读的前提是"有人看见"，
   连接建立和消息到达都不是。代价是：用户切回前台才归零，红点会多留一会儿——这是正确方向。
2. *边界在哪？* 页面可见但用户没看（比如滚动在上面，新消息在下面）仍会标已读。要更精确需要
   IntersectionObserver 逐条判断，本项目量级不值得。另：多标签页时只有一个在发已读，另一个不可见页不标。
3. *挂了怎么办？* 前端若不发 `READ`，未读数只增不减，红点常亮——是可观测的故障（不是静默错），
   用户会报"点了已读还亮着"，排查方向明确。

**H3**
1. *为什么不加缓存？* 单实例单库，一次聚合已是一条 SQL；缓存要引入失效逻辑，
   收益小于复杂度。"不加 Redis"是本项目的既定约束。
2. *边界在哪？* 索引对 `deleted=0` 这类低选择性条件帮助有限，真正吃索引的是 `appointment_date` 等值。
   数据量到十万级时，趋势图的 `BETWEEN` 区间聚合会变慢，届时要考虑按天预聚合。
3. *挂了怎么办？* 索引缺失时查询仍正确，只是退化为全表扫；迁移失败不影响功能，可先上代码后上索引。

**H4**
1. *为什么不上 Micrometer？* 单实例没有跨服务调用要串，为一行号引入整套链路追踪不划算。
2. *边界在哪？* 定时任务与 WebSocket 回调没有 HTTP 请求上下文，日志里追踪号为空；
   需要的话可以在任务入口自己塞一个。
3. *挂了怎么办？* 上游网关不透传 `X-Trace-Id` 时各自生成新号，单次请求内仍可定位，
   只是跨系统串联断掉——不影响本系统内的排查。
