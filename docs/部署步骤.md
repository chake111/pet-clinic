# 部署步骤

从零把这套系统跑起来，到能在浏览器里走完"注册 → 挂号 → 支付 → 问诊 → 病历 → 评价"。
本机开发看第 1~6 节就够了，第 7 节是一台 Linux 服务器上的生产部署方式，第 8 节是常见问题。

> 想跳过本机安装直接用 Docker：按 README 的“Docker 一键启动（演示环境）”执行。先 `cp .env.example .env` 填入三个变量，再 `docker compose up -d --build --wait`；三条命令、访问地址与数据清理方式都在 README。本节起是本地开发与手工生产部署。

## 1. 环境要求

| 依赖 | 版本 | 校验命令 | 说明 |
| --- | --- | --- | --- |
| JDK | 17 | `java -version` | Spring Boot 3 不支持 JDK 8/11 |
| Maven | 3.6+ | `mvn -v` | 或直接用 IDEA 内置的 Maven |
| MySQL | 8.0+ | `mysql --version` | 项目基线是 MySQL 8，建表脚本按 8.0 编写；更低版本未验证过 |
| Node.js | 18+（实测 24） | `node -v` | Vite 5 的最低要求是 18 |
| 浏览器 | Chrome / Edge 近版本 | — | WebSocket 与 CSS 容器查询 |

后端不需要 Maven 之外的全局配置，前端不需要 pnpm/yarn，`npm` 即可。

## 2. 端口与路径约定

先把这几个值记住，后面所有报错都和它们有关：

| 项 | 值 | 定义位置 |
| --- | --- | --- |
| 后端端口 | `8081` | `application.yml` → `server.port`（本机 8080 被别的 Java 服务占了，所以不用默认值） |
| 后端上下文 | `/api` | `application.yml` → `server.servlet.context-path` |
| 前端 dev 端口 | `5173` | `vite.config.js` → `server.port` |
| 接口前缀 | `http://127.0.0.1:8081/api/...` | 上两项拼起来 |
| 图片访问前缀 | `/api/uploads/...` | `application.yml` → `petclinic.upload.url-prefix` |
| 图片落盘目录 | 进程工作目录下的 `uploads/` | `petclinic.upload.dir: ./uploads` |

两个容易搞错的点：

- 后端上下文自带 `/api`，Vite 代理**只做转发、不做 rewrite**，把前缀原样留给后端。前端不手写 `/api/xxx`：公共 HTTP 实例（`frontend/src/api/http.js`）以 `/api` 为 baseURL，各 API 封装只写业务路径（如 `/admin/doctors`），发出时统一拼成 `/api/...`。但 `/api` 不止写在 baseURL 一处——改 `context-path` 时要连同 `vite.config.js` 的代理键、WebSocket 握手地址、`petclinic.upload.url-prefix`（含静态映射）一起核对，漏改哪处哪处就打到旧地址；dev 与生产同域反代下拼出的路径相同，业务代码不需要改。
- `./uploads` 是**相对 JVM 工作目录**，不是相对 jar 或源码。从 `backend/` 目录启动，图片就落在 `backend/uploads/`；从项目根目录启动，就落在 `./uploads/`。换目录启动会"看不见"之前上传的图片。

## 3. 建库与导数据

两个脚本，顺序不能反：`02_data.sql` 只 `USE pet_clinic`，表不存在会直接报错。

```bash
# 建表（脚本自带 DROP DATABASE IF EXISTS + CREATE DATABASE，不需要手工建库）
mysql -uroot -p --default-character-set=utf8mb4 < sql/01_schema.sql

# 种子数据
mysql -uroot -p --default-character-set=utf8mb4 pet_clinic < sql/02_data.sql
```

注意 `--default-character-set=utf8mb4`：Windows 的 mysql CLI 默认按 gbk 发语句，漏掉这个参数，中文数据会变成问号或乱码，而前端页面看起来只是"数据奇怪"，不容易联想到导入环节。

**重跑会清空全部数据**（包括你在界面上注册测试出来的账号、下的单、聊过的消息）。这不是 bug，是脚本首行的 `DROP DATABASE IF EXISTS`。要保留数据就别再执行 `01_schema.sql`。

用 Navicat / DataGrip / DBeaver 导入也一样：先 01 再 02，并且确认连接的字符集是 utf8mb4。

导完核对一下：

```bash
mysql -uroot -p --default-character-set=utf8mb4 -e "
USE pet_clinic;
SELECT COUNT(*) AS tables_now FROM information_schema.tables WHERE table_schema='pet_clinic';
SELECT COUNT(*) AS doctors FROM doctor;
SELECT COUNT(*) AS sched_has_remain FROM doctor_schedule WHERE remain_num > 0 AND work_date >= CURDATE();
"
```

期望：表数与 `sql/01_schema.sql` 里的 `CREATE TABLE` 条数一致；医生 12 位（种子数据写死的数量）；当日及以后有剩余号源的排班不为 0。最后一项为 0 说明种子数据里"日期相对 CURDATE() 生成"那段没执行成功——`02_data.sql` 的排班是相对当天写的，任何时候导入当天都有号可约。

**已建库升级（不重导全库）**：如果库是早于 2026-09-15 的版本导入的，执行下面的增量 SQL。它不只加列：`UPDATE notice` 会**回填**存量公告的发布人（已发布且 `publish_by` 为空的行补 1），`DROP TABLE IF EXISTS sys_dict` 会**删掉**系统字典表及其数据。两者都在改已有数据，执行前先备份一次（结构 + 全量数据），出问题靠备份回滚：

```sql
ALTER TABLE consult_session
  ADD COLUMN moderate_status TINYINT NOT NULL DEFAULT 0 COMMENT '管理员处置 0正常 1无效关闭 2违规屏蔽(非0即参与方不可见)' AFTER status,
  ADD COLUMN moderate_reason VARCHAR(255) DEFAULT NULL COMMENT '处置原因' AFTER moderate_status,
  ADD COLUMN moderate_by BIGINT DEFAULT NULL COMMENT '处置人 admin_user.id' AFTER moderate_reason,
  ADD COLUMN moderate_time DATETIME DEFAULT NULL COMMENT '处置时间' AFTER moderate_by;
ALTER TABLE consult_message
  ADD COLUMN hidden TINYINT NOT NULL DEFAULT 0 COMMENT '0正常 1已屏蔽(参与方不可见, 管理员仍可见)' AFTER is_read,
  ADD COLUMN hidden_reason VARCHAR(255) DEFAULT NULL COMMENT '屏蔽原因' AFTER hidden,
  ADD COLUMN hidden_by BIGINT DEFAULT NULL COMMENT '处置人 admin_user.id' AFTER hidden_reason,
  ADD COLUMN hidden_time DATETIME DEFAULT NULL COMMENT '屏蔽时间' AFTER hidden_by;
ALTER TABLE notice
  ADD COLUMN publish_time DATETIME DEFAULT NULL COMMENT '首次发布时间(下架后重新发布不刷新)' AFTER view_count,
  ADD COLUMN publish_by   BIGINT   DEFAULT NULL COMMENT '首次发布人 admin_user.id; 草稿为 NULL' AFTER publish_time;
UPDATE notice SET publish_by = 1 WHERE status = 1 AND publish_by IS NULL;
DROP TABLE IF EXISTS sys_dict;
```

（`ADD COLUMN` 重复执行会报字段已存在，整段只跑一次；`UPDATE` 与 `DROP TABLE IF EXISTS` 本身幂等。全新安装直接跑 01+02，不需要这段。系统字典在 2026-09-14 下线，枚举文案改由 `frontend/src/utils/dict.js` 单点维护。）

**已建库升级（2026-09-22 排队号计数器）**：排队序号从"总量减余量"的推算值改为排班行上的 `last_queue_no` 计数器后，旧库需要执行 `sql/migrations/20260922_add_schedule_queue_counter.sql`。步骤：

1. **停写一次再执行**。脚本只加列并按该排班历史发过的最大序号初始化计数器，不改动任何既有 `appointment.queue_no`。`ADD COLUMN` 重复执行会报"字段已存在"，这是预期的防重跑信号，不要改成 `IF NOT EXISTS` 把它掩盖掉。
2. **跑脚本自带的三条迁移后自检**，每条都应为 0 行：计数器小于该排班历史最大序号的、计数为负的、没有预约却带计数器的排班。
3. **存量重复号只出清单、不改号**。脚本末段是只读查询，列出"同一排班同一序号有多张单"的分组。是否处置、怎么处置需要单独决定——号码是患者手里的历史凭证，静默改号会让旧单据与回执对不上，因此本脚本刻意不自动修号。
4. 回退只在"确认没有新单依赖该列"时执行 `DROP COLUMN last_queue_no`（脚本末行已注明）。

**旧库还有一处余量账必须单独核对（计数器脚本管不到）**：旧版本的"停诊"是把 `remain_num` 一起清零的，新版本停诊与恢复都只改状态位。因此旧库里**曾被停诊过的时段可能留着 `remain_num = 0` 的历史值**，跑完上面的计数器脚本它仍然是 0——之后点"恢复出诊"，号源不会被重新算出来，表现为这个时段一场空号。升级时按下面两步处理，先出清单再改数，不允许盲跑 `UPDATE`：

```sql
-- 诊断（只读）：存储余量与"总量 - 有效预约数"对不上的时段。
-- 有效预约口径与代码一致：未逻辑删除且状态不是已取消。
SELECT s.id, s.work_date, s.period, s.status, s.total_num,
       s.remain_num AS stored_remain,
       s.total_num - IFNULL(b.booked, 0) AS expected_remain,
       IFNULL(b.booked, 0) AS booked_active
FROM doctor_schedule s
LEFT JOIN (SELECT schedule_id, COUNT(*) AS booked
           FROM appointment WHERE deleted = 0 AND status <> 3
           GROUP BY schedule_id) b ON b.schedule_id = s.id
WHERE s.remain_num <> s.total_num - IFNULL(b.booked, 0);

-- 修复（确认上一条的清单后再执行，同样只动差异行）
UPDATE doctor_schedule s
LEFT JOIN (SELECT schedule_id, COUNT(*) AS booked
           FROM appointment WHERE deleted = 0 AND status <> 3
           GROUP BY schedule_id) b ON b.schedule_id = s.id
SET s.remain_num = s.total_num - IFNULL(b.booked, 0)
WHERE s.remain_num <> s.total_num - IFNULL(b.booked, 0);
```

改完再跑两条收尾检查：`remain_num < 0` 与 `remain_num > total_num` 都应为 0 行，然后挑一个曾经停诊的时段点"恢复出诊"，确认它按修复后的余量放出号、约满后返回"该时段号源已约满"。**这套流程在隔离测试库上完整演练过**——以下是当时的演练摘要（历史记录）：造一张 total=5 的时段、下 1 单后按旧版行为把余量清零，诊断 SQL 命中该行（stored 0 / expected 4），修复后余量回到 4，接口"恢复出诊"只改状态、余量保持 4，随后连续下单成功 4 单、第 5 单被约满拒绝，收尾两条不变量 0 行，测试数据按 run tag 全部删除、差异清单回到 0 行。演练脚本与逐行输出当时放在 `.tmp/` 临时目录，未纳入版本库、原始材料现已不保留；要复核请按上面的诊断/修复 SQL 在隔离测试库重跑一遍。

**已建库升级（2026-10-01 删除医生工号列）**：`doctor.emp_no` 已从表、代码与文档中整体移除，旧库需执行 `sql/migrations/20261001_drop_doctor_emp_no.sql`，正文就一句 `ALTER TABLE doctor DROP COLUMN emp_no`。执行前先按迁移文件头给出的核对 SQL 确认列还在（MySQL 8.0 不支持 `DROP COLUMN IF EXISTS`）：查到 1 行才执行，0 行说明已删过、直接跳过。删列无法用事务回滚撤销，回滚只能靠迁移前留的备份（结构 + 全量数据 + id→emp_no 映射）按 id 回填，因此执行前先备份一次。

**已建库升级（2026-10-19 令牌撤销与未读校准）**：按顺序做两步。

1. 发布前执行 `sql/migrations/20261019_add_token_version.sql`：`sys_user` 与 `admin_user` 各加一列 `token_version`（`NOT NULL DEFAULT 1`，存量账号自动获得版本 1）。缺这一列时，登录与鉴权会在查询处直接报错，不会静默放行。
2. 发布完成后执行 `sql/migrations/20261019_refresh_unread_counters.sql`：按可见未读消息重算 `consult_session.user_unread / doctor_unread`，校准旧逻辑留下的漏记。文件里带执行前后的核对 SQL，后置查询应返回 0 行。

第二步放在发布之后，是因为旧代码在发布完成前仍可能产生新的漏记；先发布再校准只需做一次。回退时保留 `token_version` 列即可（旧版本不读取它），未读计数重新执行同一脚本即可对齐。

**已建库升级（2026-11-16 下单幂等键与清扫任务租约）**：发布新代码前先执行两个迁移，顺序不限。

1. `sql/migrations/20261116_add_appointment_idem_key.sql`：`appointment` 加 `idem_key` 列与 `uk_user_idem (user_id, idem_key)` 唯一索引。列可空，历史单不需要回填（MySQL 唯一索引允许多个 NULL）；重复执行会报重复列/重复索引，属于预期的防重跑信号。
2. `sql/migrations/20261116_add_scheduler_lease.sql`：新建 `scheduler_lease` 表。清扫任务每轮都要读写它，缺表时任务会报错——业务请求不受影响，但超时单不会自动取消。

两个脚本末尾都有自检查询。必须先迁移再发版：新代码的下单插入会写 `idem_key`，清扫任务会读写租约表。

全新安装不需要这几节：`01_schema.sql` 已含计数器列、已不含 `emp_no`、已含 `token_version`、已含 `idem_key` 与 `scheduler_lease`，且新写入不存在旧版停诊清零余量的问题。

## 4. 需要改的配置

`application.yml` 里的数据库口令仍是开发机自用的"带默认值占位"（`${DB_PASSWORD:123456}`），`git clone` 后只需再给一个 JWT 密钥即可起演示；真实部署换掉这两处：

```yaml
spring:
  datasource:
    username: ${DB_USERNAME:root}          # ← 生产用环境变量覆盖
    password: ${DB_PASSWORD:123456}        # ← 生产必须换（默认值仅本机演示）
petclinic:
  jwt:
    secret: ${JWT_SECRET:}                 # ← 无默认值，未注入即启动失败
    expire-seconds: 604800                 # 7 天
```

- `jwt.secret` 用 HMAC-SHA 签名（jjwt 按密钥长度自动选 HS256/384/512），要求 ≥ 32 字节。**代码里不再保留任何默认密钥**：启动阶段会拒绝空值、不足 32 字节，以及历史上公开过的两个示例值（`pet-clinic-hs256-secret-please-change-in-production-2026`、`pet-clinic-default-dev-secret-key-change-me`）。本地开发也要先 `export JWT_SECRET=...`，否则启动即失败——这是刻意设计的，避免"忘了配却以为配了"。
- 改了 `jwt.secret` 会让所有账号重新登录；只改某个账号的密码则只撤销该账号的旧令牌，见 4.2。
- `petclinic.scheduler.lease-seconds`（默认 300，必须 > 0）控制清扫任务租约有效期。正常一轮远小于它；调大只会拉长实例崩溃后的接管等待，不会提高正确性；配成 0 或负数会在启动期被 `@Min(1)` 拦下。
- `serverTimezone=Asia/Shanghai` 要和 MySQL 服务端时区一致，否则"今日号源"会差一天。
- 端口冲突时改 `server.port`，同时改 `vite.config.js` 的 `BACKEND`；两处不一致的症状是页面能打开、所有接口转圈或 502。

### 4.1 生产凭据注入

仓库里**只保留开发默认值**，生产凭据一律从外部注入（`application-prod.yml` / `application-local.yml` 都已在 `.gitignore` 里，不会误提交）：

| 环境变量 | 覆盖项 | 说明 |
| --- | --- | --- |
| `DB_USERNAME` | `spring.datasource.username` | 默认 `root` |
| `DB_PASSWORD` | `spring.datasource.password` | 默认 `123456`，仅本机演示 |
| `JWT_SECRET` | `petclinic.jwt.secret` | **必填，无默认值**；≥ 32 字节（算法随长度自动选：32B→HS256、48B→HS384、64B→HS512）；空/过短/历史示例值均启动失败 |

注入方式二选一：

```bash
# 方式一：环境变量（注意：同名时命令行属性优先级更高，--petclinic.jwt.secret=xxx 会盖掉环境变量）
DB_USERNAME=petapp DB_PASSWORD='...' JWT_SECRET='...' java -jar pet-clinic-server.jar

# 方式二：外部 prod 配置——把 application-example.yml 复制为**启动工作目录下的** config/application-prod.yml，
# 填好后走 profile。放在 config/ 是因为 Spring Boot 会加载 jar 之外的 config/ 目录，
# 且其优先级高于 jar 内配置——改凭据不用重新打包（这正是外部注入的目的）
java -jar pet-clinic-server.jar --spring.profiles.active=prod
```

配置不生效时按优先级从高往低逐层对：命令行属性 > 环境变量 > `config/` 外部文件 > jar 内 `application.yml`。顺序记反了会往错误方向排查（盯着环境变量找，其实被启动参数盖掉了），所以排错先确认最高层有没有同名值。

`application-example.yml` 里这两项写成**无默认值**的 `${DB_PASSWORD}` / `${JWT_SECRET}`：按模板配 prod 时，少注入一个就直接启动失败，避免"忘了改却以为改了"。jar 内的 `application.yml` 现在也只有 `JWT_SECRET` 一个必填项，数据库口令仍是本机演示默认值。

注意：这两个变量名是**通用名**，同一台机器上跑多个项目会互相覆盖——如果本项目的启动行为与 `application.yml` 里写的不一致（比如改了 secret 但不生效），先用 `echo $JWT_SECRET`（Windows 下 `set JWT`）确认环境里有没有同名变量在顶掉配置。

### 4.2 令牌撤销规则与升级

账号表（`sys_user` / `admin_user`）各有一列 `token_version`，登录时签进 JWT 的 `ver` 声明；`AccountGuard` 每次校验都比对库中当前值与令牌声明。

| 操作 | 效果 |
| --- | --- |
| 账号本人改密 | 同一条 UPDATE 内密码 + `token_version + 1`，该账号此前签发的令牌立即失效，需重新登录 |
| 管理员停用账号 | 已有行为，下一次请求即被拒 |
| 轮换 `jwt.secret` | 所有账号的令牌一并失效 |

**升级顺序**：先执行 `sql/migrations/20261019_add_token_version.sql`（列带默认值 1，存量账号自动获得版本 1），再发布应用。新版本不接受缺少 `ver` 声明的旧令牌，因此发布后所有在线用户需要重新登录一次——请安排在无进行中问诊的维护窗口。

**回退**：保留新增列即可，旧版本应用不读取它。但回退后改密不再撤销旧令牌，如需保持撤销能力，回退的同时轮换 `jwt.secret`。

可按需调整的业务参数（同文件）：

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `petclinic.upload.dir` | `./uploads` | 图片落盘目录 |
| `petclinic.upload.url-prefix` | `/api/uploads` | 库存的 URL 前缀，改了要同步静态映射（见 `WebMvcConfig#resourcePattern`） |
| `petclinic.upload.max-size-bytes` | `5242880` | 单张 5MB。注意外层还有 `spring.servlet.multipart.max-file-size: 10MB` |
| `petclinic.pay-timeout-minutes` | `30` | 未支付自动取消的时限 |

联调要看 SQL 时，把 `application.yml` 里 `mybatis-plus.configuration.log-impl` 那行注释打开（控制台打印 SQL），看完再关掉，否则高并发下日志量很大。

## 5. 启动后端

**IDEA**：运行 `PetClinicApplication#main`，Working directory 选 `backend`（决定 uploads 落在哪）。

**命令行**：

```bash
cd backend
mvn spring-boot:run
```

首次构建要联网下载依赖。依赖都在 Maven 中央仓库，没有私有仓库配置；本仓库离线验证时用的是 `mvn -o`，正常开发不需要加。

打成可执行 jar：

```bash
cd backend
mvn clean package
# 产物：backend/target/pet-clinic-server.jar（finalName 固定，不带版本号）
java -jar target/pet-clinic-server.jar
```

生产上带覆盖参数启动：

```bash
java -jar pet-clinic-server.jar \
  --spring.datasource.password='真实密码' \
  --petclinic.jwt.secret='至少32字节的随机串' \
  --petclinic.upload.dir=/data/pet-clinic/uploads
```

**验证后端起来了**（这两个接口在白名单里，不需要 token）：

```bash
curl -s http://127.0.0.1:8081/api/client/catalog/home | head -c 120
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8081/api/swagger-ui/index.html
```

第一条返回 `{"code":200,...}`，第二条返回 `200`。浏览器打开 http://127.0.0.1:8081/api/swagger-ui/index.html 就是 Swagger UI 接口文档，可以在这里直接试接口（需要登录态的接口请用 curl/Postman 带上 `Authorization: Bearer <token>`）。

启动后有两类定时任务在跑（`task/AppointmentSweepTask`）：每 60 秒把超时未支付的单取消并回滚号源，每天 00:30 把**已支付、过了就诊日、仍待接诊**的单标为未到诊（候选 SQL 是 `AppointmentMapper.selectStaleVisitIds`，锁内复核同一口径）。只收这三个条件是有原因的：已接诊的单不改判——医生已经动过手，改成未到诊会抹掉真实诊疗记录；未支付的过期单归超时清扫负责取消并退号，两条路互不重叠，谁先跑都不改变终态。每轮先抢 `scheduler_lease` 里的租约（任务名 `appointment.expire-unpaid` / `appointment.mark-missed`），只有抢到的实例真正扫描，其余实例跳过；租期默认 300 秒（`petclinic.scheduler.lease-seconds`），用数据库时钟计算，持有进程挂掉后最多 5 分钟由其他实例接管。租约只决定"谁跑这一轮"，单张预约的退号/改状态仍由预约行锁与条件更新保证，重复执行不会重复退号。图文问诊的连接注册表与消息投递状态仍保存在进程内（`websocket/ConsultSocketRegistry` 就是一张内存 Map），多实例需要粘性会话或共享通道，这部分本次没有改。

## 6. 启动前端

```bash
cd frontend
npm install
npm run dev
```

`vite.config.js` 里 `server.open: true`，正常情况下会自动打开 http://127.0.0.1:5173。没弹出来就手动访问。

后端不在 8081 时，用环境变量指过去：

```bash
# Git Bash / Linux
VITE_BACKEND=http://127.0.0.1:8090 npm run dev
# PowerShell
$env:VITE_BACKEND="http://127.0.0.1:8090"; npm run dev
```

这里有个坑：`vite.config.js` 读的是 `process.env.VITE_BACKEND`，只认**真实的 shell 环境变量**。写个 `.env` 文件放项目里是没用的——Vite 会把 `.env` 注入 `import.meta.env`（给浏览器端代码用），不会回填到 `process.env`。不想设环境变量就直接改 `vite.config.js` 里的默认值。

代理转发失败时 Vite 不会崩，控制台会打 `[proxy] 后端不可达 /api/xxx ECONNREFUSED`，浏览器表现为所有接口 pending 或 502。看到这行就是后端没起或端口不对。

## 7. 生产部署（同域反向代理）

前端构建产物是纯静态文件，不需要 Node 常驻。

```bash
cd frontend && npm run build     # 产物 frontend/dist，实测 10s 左右
```

这里有个坑：部分 Windows 机器上构建会在 `[vite:esbuild-transpile]` 阶段报 `remove C:\...\Temp\esbuild-xxxx: Access is denied.` 然后失败，退出码 1，并在临时目录遗留一批 `esbuild-<64 位哈希>` 文件。esbuild 对超过 1MB 的 chunk 走"临时文件中转"（JS 端写入、Go 端读取后立即删除），本机上这一步删除持续失败，具体占用来源尚未确认——本机装有 Defender 与联想/火绒等实时防护，但未定位到持有句柄的进程；换 TEMP 到其他盘、写后延迟交付也都无效。已核对上游最新 esbuild 源码，删除失败仍是直接报错、无重试，升级能否解决未实测。当前作为本机构建的绕行措施：前端内置 `frontend/esbuild-tmp-shim.cjs` 让 esbuild 改走管道内联输入、不落临时文件（走的是 0.21.5 已有的失败降级路径，3MB 级输入实测正常），`npm run dev` / `npm run build` 自动加载；构建时间与产物不变，临时目录无残留。该 shim 依赖 esbuild 的临时文件命名与降级行为，升级 esbuild 后运行 `npm run build`，确认大体积产物仍能正常构建。要恢复 esbuild 原行为：把 `frontend/package.json` 里这两个脚本的 `node -r ./esbuild-tmp-shim.cjs node_modules/vite/bin/vite.js` 改回 `vite` / `vite build`；若想从占用来源一侧解决，先确认持有临时文件句柄的进程，再在对应杀软中给 `%TEMP%\esbuild-*` 加扫描排除。

推荐用 nginx 把前后端放在同一个域名下，这样浏览器只访问 80，没有跨域、没有第二套 token 存储问题：

```nginx
server {
    listen 80;
    server_name pet.example.com;

    # 前端：history 路由必须回退到 index.html，否则刷新 /admin/doctors 会 404
    location / {
        root /data/pet-clinic/dist;
        try_files $uri $uri/ /index.html;
    }

    # 后端：context-path 已经是 /api，所以 proxy_pass 不带路径，原样转发
    # 指标端点只在容器/内网给 Prometheus 抓取，不从公网 nginx 放出去
    location /api/actuator/metrics { return 404; }
    location /api/actuator/prometheus { return 404; }

    location /api/ {
        proxy_pass http://127.0.0.1:8081;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        client_max_body_size 10m;      # 与 multipart.max-file-size 对齐
        proxy_read_timeout 300s;       # 长连接别被过早掐断
    }
}
```

`Upgrade`/`Connection` 两个头是图文问诊的 WebSocket 必需的。握手地址是 `ws://域名/api/ws/consult?token=...`，少了这两个头会连不上，前端表现为聊天面板反复重连。

配好之后访问 `http://域名/`（用户端）和 `http://域名/admin/login`（后台）。

其他生产事项：

- 后端用 systemd 或 `nohup java -jar ... ` 拉起，工作目录固定，`petclinic.upload.dir` 建议写成绝对路径，避免下次换启动目录图片"消失"。
- `uploads/` 是唯一有状态的东西，换机器只要拷这个目录 + `mysqldump pet_clinic`。图片不接对象存储，是本系统明确的范围边界。
- 种子数据里的演示账号（`admin` / `doctor01` / `zhangsan`，密码统一 `123456`）上线前要么删掉要么改密。
- `logging.level.com.petclinic: debug` 上线改 `info`。
- 日志每行带追踪号（`ERROR [9d47a390…] …`），同一个号也在 `X-Trace-Id` 响应头与 500 响应的提示里。用户报障时让他给出提示里的号，`grep <号> 应用日志` 就能拿到那次请求的完整堆栈——多个前端实例、多次重试混在一起时靠它区分。上游有网关的话，把入站 `X-Trace-Id` 透传下来即可全链路同号。

### 7.1 可选观测栈（演示环境）

Prometheus 和 Grafana 放在 compose 的 `observability` profile 里，默认 `docker compose up` 不会启动：

```bash
docker compose --profile observability up -d db backend prometheus grafana
# Prometheus http://127.0.0.1:9090
# Grafana    http://127.0.0.1:3000
```

两个服务只绑 `127.0.0.1`，不发布到局域网；Grafana 默认口令 `admin` 仅适用于本机，可用 `PETCLINIC_GRAFANA_PASSWORD` 覆盖，不要改成 `0.0.0.0`。面板和数据源都由文件 provision，Prometheus/Grafana 没有命名卷，`docker compose --profile observability down` 即清掉观测数据。

后端健康端点分三个用途：

- `/api/actuator/health`：聚合状态，经 nginx 可访问，兼容旧检查。
- `/api/actuator/health/liveness`：只看进程，数据库挂掉仍是 200。
- `/api/actuator/health/readiness`：显式包含 `db`，数据库不可用时返回 503；compose 的 backend healthcheck 用的就是它。

`/api/actuator/metrics` 和 `/api/actuator/prometheus` 由 nginx 返回 404，只在容器网络内可见；Prometheus 直接抓 `backend:8081`，不经过 nginx。

## 8. 常见问题

**接口全部 404，只有 `/api/swagger-ui/index.html` 能打开**
`context-path` 和请求前缀没对上。浏览器 Network 里确认实际发出的路径是不是 `/api/client/...`；把 `server.servlet.context-path` 改掉时，Vite 代理与 `petclinic.upload.url-prefix` 都要同步。

**上传成功但图片 404**
先确认文件真的落盘了（`<工作目录>/uploads/`）。如果文件在、URL 打不开，是静态资源映射注册的模式没剥掉 `context-path`：Spring 的 `addResourceHandler` 在 `context-path` **之内**匹配，`/api/uploads` 要注册成 `/uploads/**`，否则真实地址变成 `/api/api/uploads/**`。代码里 `WebMvcConfig#resourcePattern` 已处理，改动配置时别破坏这个前提。

**登录成功，但下一秒就 401 / 权限错乱**
用户端和后台是两套 token（`sys_user` 与 `admin_user`）。把患者 token 用在 `/admin/**` 上会被拦截器拒。前端用同一个 axios 实例按 URL 前缀选 token，所以两边可以同浏览器并存；手工用 curl/Postman 测试时要各自取各自的 token。

**改了密码，旧 token 还能用**
不再是预期行为。改密时 `token_version` 递增，旧令牌在 REST、WebSocket 握手、入站帧和出站帧四处都会被 `AccountGuard` 拒绝。若观察到旧令牌仍可用，先确认升级时执行了 `20261019_add_token_version.sql`（缺列时后端启动会因 SQL 报错直接失败，不会静默放行）。

**后台管理员点接诊/写病历/已读，返回 403**
这些是临床动作，只给 `DOCTOR`：接诊、结束就诊、书写与修订病历、会话发言与已读都按登录人的 `doctor_id` 隔离数据，管理员没有医生身份，接口层的 `@RequireRole` 先拦、服务层再复核一次（两层各挡一面，去掉注解仍会被服务层拒）。管理员保留的是查阅与前台业务：看完整病历与工单、代患者取消**尚未接诊**的单子、治理会话与评价。病历删除对管理员和医生都返回 403——病历是诊疗记录，后台不提供删除，写错了由医生在原单上修订。管理员若要进接诊工作台，前端路由也会直接重定向回看板，不用等接口报错。

**账号停用后的连接处理**
`AccountGuard` 在 REST 请求、WebSocket 握手及收到消息帧时校验账号状态。已有连接在下一条消息或心跳到达时返回停用提示并关闭，前端心跳间隔为 30 秒。

**医生列表/看板显示"离线"，但人正在聊天**
`doctor.online_status` 由 WebSocket 连接建立/断开维护。后端重启会把库里的值留在上次状态，且不会自动恢复。这是单实例下的已知边界，重连一次即纠正。

**中文全乱码**
依次查三处：导入时 mysql CLI 有没有 `--default-character-set=utf8mb4`；JDBC URL 的 `characterEncoding=utf8` 有没有被改掉；表/库是不是 `utf8mb4_general_ci`（`01_schema.sql` 已固定）。

**`npm run dev` 起在 5174 而不是 5173**
端口被占，Vite 自动顺延。功能无影响；要严格固定就改 `vite.config.js` 的 `server.port`，或先释放 5173。

**`mvn` 卡在下载或报缺包**
网络问题。本系统依赖全在中央仓库，不需要私有镜像；有代理就配 `~/.m2/settings.xml`。确认能连通后重跑 `mvn clean package`。

**并发抢同一个号超卖？**
不会出现。扣号是一条 `UPDATE doctor_schedule SET remain_num = remain_num - 1 WHERE id=? AND status=1 AND remain_num>0`，靠行锁与条件判断保证。
